# Git 工作流与交接规则

此规则来自用户明确要求：**动手前确保可回滚；用户验收通过后提交版本；每完成一项更新计划表。**
任务状态唯一台账为根目录 [PLAN.md](../PLAN.md)，事实摘要为 [STATUS](STATUS.md)。

## 1. 开工前建立回滚点

先确认目录、当前分支、远端和工作区，查看已有记录：

```sh
git status --short --branch
git log -5 --oneline
git remote -v
git rev-parse HEAD
```

- 若干净：把当前 HEAD 记录为任务基线，这已经是可回滚点，不需要空提交。
- 若有本任务或用户留下的未提交项目改动：先逐文件检查，排除缓存、凭据和导出包，创建 `checkpoint(Pxx): ...` 提交，再开始修改。快照可以是未验证状态，但必须明说，不得当成验收版本。
- 若发现其他 agent 正在写同一目录：不把对方未完成内容悄悄混进本任务；使用独立分支/工作副本，或协调归属。分支隔离不能让多个 agent 同时安全写同一份文件。
- 不以 stash 作为唯一长期回滚点，不用 reset --hard/clean 丢弃用户修改。
- 本次用户已授权将现有完整项目保存为初始提交；后续仍要检查具体变更范围。

开始后更新 PLAN 的状态、负责人、分支、基线 SHA 和本轮范围；可另建 `task/pXX-description` 分支，若继续现有任务则沿用并记录。不重置已有分支。

## 2. 实现与自测

保持每次可验收范围小。共享状态与视图规则按 AGENTS 和 ARCHITECTURE。
对代码运行必要测试与画面验证；文档改动检查事实和链接。失败应修复或明确记录，不能把“启动成功”写成玩法通过。
若 Godot 编辑器提示外部文件变化，重新加载磁盘文件，防止旧缓冲区覆盖脚本；重大场景结构变更时给用户明确操作说明。

## 3. 交付等待验收

更新 PLAN、STATUS，以及受影响的 DECISIONS/README/架构说明；写明实际完成、测试、限制、用户操作步骤。
检查并按具体文件暂存：

```sh
git diff --check
git diff --stat
git status --short
# git add <已检查的具体文件>
# git commit -m "feat(Pxx): ..." 或 "fix(Pxx): ..."
```

提交说明写用户可见行为及原因。计划状态写“待验收”，不能因为 agent 自测通过就写“已验收”。
告知用户如何运行与验收，提供实现提交号；提交本身的 SHA 无法写入其自身文件，后续记录或验收记录中再填写。

## 4. 用户验收后必须再提交

用户明确通过后核对验收对象；若代码已变化，先确认新增改动是否属于已验收范围，不把别人的新工作夹带进去。

1. PLAN 改为“已验收”，写用户确认的依据及被验收的实现提交；STATUS 更新下一步。
2. 暂存这次验收记录，创建 `accept(Pxx): record user acceptance` 提交。即使代码未变，也有这份验收文档变更需要提交。
3. 给这个提交建立 `accepted/pXX` 注释标签，标签说明包含验收依据；若已存在，使用新的修订名，不强行移动旧标签。
4. 当次授权包含远端同步时，推送相应分支与明确标签，并核对远端 SHA。不能以“本地提交成功”宣称已上传。

若用户要求修改，把任务改“需修改”，修复后再次自测、提交并等待验收。

## 5. 回滚原则

- 先保留当前进度，再决定恢复方式。记录“能回滚”不代表默认执行回滚。
- 查旧版优先在另一个工作副本检出，避免破坏当前工作目录。
- 已共享到远端的历史优先通过 revert 产生反向提交；不要强推覆盖别人历史。
- 真正需要丢弃未提交内容、重写共享历史或覆盖远端时，明确影响并取得针对性授权。

## 6. 多 agent 同步

每个 agent 开始时读 AGENTS → PLAN → STATUS → 相关设计和代码。一次任务结束必须更新台账，不依赖聊天上下文传递完成情况。
远端可用且任务包含同步时先 fetch，再检查分支差异；不能在有未保存内容时盲目 pull，也不能覆盖远端新增提交。
计划中的依赖是实际行为依赖；前置功能尚待用户验收时先处理反馈，独立工作可另行授权并行。

新会话可使用：

> 请先读 AGENTS.md、PLAN.md 和 STATUS.md，核对 Git 与实际代码。执行 Pxx，在动手前记录可回滚提交；按计划验收要求实现并验证，完成后更新计划和状态、创建实现提交并给我操作步骤。收到我验收通过后，再记录验收并提交版本。
